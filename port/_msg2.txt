Port the favorability tools and restore their manual page

The three creative-only debug items that upstream registers as
FAVORABILITY_TOOL_ADD / _REDUCE / _FULL, plus the held-back Patchouli entry that
documents them. Base game + book now at 40 entries / 3 categories.

What the tools do, copied from upstream event/maid/UseFavorabilityToolEvent:

  add    -> FavorabilityManager#add(point)               (clamped by level cap)
  reduce -> FavorabilityManager#reduceWithoutLevel(point)
  full   -> FavorabilityManager#max()                    == add(LEVEL_3_POINT)

point is 1 while sneaking, 64 otherwise. reduceWithoutLevel is the deliberate
choice upstream made for the tool: plain reduce() clamps at the *current* level's
floor, so the tool would look like it stopped working once she reached a level
boundary.

Implementation notes:
- One class, ItemFavorabilityTool, with a "type" string; the item itself is inert
  (isFoil true, one grey tooltip line keyed by type) exactly like upstream.
- The behaviour lives in EntityMaid#useFavorabilityTool and is called from
  mobInteract right after feedGoldenApple. That is the same slot the Forge-side
  InteractMaidEvent handlers occupy: upstream's UseFavorabilityToolEvent is a
  NORMAL-priority subscriber, ahead of SaddleMaidEvent / UseNameTagEvent and well
  ahead of the sneak branches (DismountMaidEvent LOW, SwitchSittingEvent LOWEST).
- FavorabilityManager#max() is not invented: upstream is literally
  "this.add(LEVEL_3_POINT)". Reusing add() also refreshes ATTACK_DAMAGE /
  MAX_HEALTH and fires the level-up sound, which a hand-written assignment would
  have to duplicate.
- The PLAYER_LEVELUP sound is played unconditionally, so a click that levels her
  up plays it twice. That is upstream behaviour, kept as is.

Book side:
- port/book_pages_held_back/other/favorability_tool.json is back in place.
- overview/favorability's icon goes from the temporary minecraft:cake back to the
  upstream favorability_tool_add, which can finally resolve to a real item.
- validate-book.ps1 now knows the three ids. Output: entries=40 categories=3
  problems=0.

Deviations from upstream, all API-level only: FabricItemSettings instead of
Item.Properties().tab(...), and stacksTo(1) without durability (unchanged).

Verified: gradlew build green; the three models / textures / mcmeta, the item
class and the restored entry are all inside the jar; runClient boots with 194
maid models, 58 chair models, "BookContentResourceListenerLoader preloaded 44
jsons" and no "Error compiling book", no unknown item ids, no exceptions.
