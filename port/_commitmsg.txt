Teach the manual to render altar recipes, and fix 16 dead altar recipes

The Patchouli side of the altar was believed to be a placeholder. It was not:
AltarRecipeComponent already resolved recipe_id -> AltarRecipe and emitted the six
ingredient slots, the power cost, the item output and the entity output. The one
real gap was upstream's special case, "if the output entity is a box, draw a maid
instead" -- skipped earlier because EntityBox had not been ported. It has now, so
the branch is back and spawn_box's page shows a maid rather than an empty box.

Chasing that turned up a much worse bug in the data, not the rendering.

Upstream writes Forge's own tags in the altar recipes: forge:gems/diamond,
forge:ingots/gold, forge:dyes/red and so on. The port renamed them all to the
Fabric conventional names (c:diamonds, c:gold_ingots, c:red_dyes ...) but only
created 9 of the 21 tag files. The other 12 were never defined:

    diamonds emeralds lapis redstone_dusts gold_ingots iron_ingots
    blue_dyes cyan_dyes lime_dyes orange_dyes red_dyes yellow_dyes

An undefined tag is not an error at load time. It silently resolves to an empty
tag collection, so Ingredient#getItems() returns a zero-length array -- and
because that array is not Ingredient.EMPTY, RecipeMatcher does not treat it as a
padding slot, so findMatches can never succeed. Result: 16 of the 27 altar
recipes were impossible to craft, including reborn_maid (the shrine revival, the
mod's core mechanic) and spawn_box (summoning a maid), and the matching pages
drew empty ingredient slots. Nothing in the log said a word.

I confirmed the environment has no other source for these tags: Fabric API
0.77.0 ships zero files under data/c/tags/ in any of its modules (checked by
opening every jar in the Gradle module cache). So c: is entirely ours and a
missing file is a dead recipe.

Changes:
- Add the 12 missing tag files (port/add-missing-c-tags.ps1 generates them and
  verifies each one parses and has at least one value).
- Restore the box -> maid branch in AltarRecipeComponent.
- Extend validate-book.ps1 beyond spotlight items / icons / entity pages: it now
  also checks that every altar_recipe page names a recipe that exists, that every
  c: tag used by a recipe is actually defined, and that a recipe's ingredients
  and output refer to registered ids. Verified both ways -- deleting diamonds.json
  makes it print three ALTAR EMPTY c: TAG lines and problems=3.
- Correct the two documents that described the old state (the README's known-issues
  section and port/book_pages_held_back/README.md, which also said "14 pages"
  where there are 13). The README now records why an empty c: tag is worse than a
  missing page: it breaks crafting rather than rendering.

Verified: gradlew build green; the 21 tag files and the recompiled component are
inside the jar; runClient boots with no "Altar recipe not found", no
"Error compiling book", no unknown item ids -- only the usual "No data fixer
registered" lines every mod gets. validate-book.ps1 reports entries=39
categories=3 problems=0.
